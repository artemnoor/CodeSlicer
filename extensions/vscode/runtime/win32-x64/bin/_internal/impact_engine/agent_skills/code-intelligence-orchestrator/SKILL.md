# Code Intelligence Orchestrator

Сначала определите тип задачи и используйте установленный каталог skills/инструментов CodeSlicer. Не предполагается, что checkout находится по пути `.agents/skills`: это правило должно работать и для wheel-пакета.

## Выбор инструмента

| Задача | Основной инструмент | Результат |
|---|---|---|
| Новый или незнакомый проект, модули, документация, ADR, сообщества | Graphify | Архитектурная карта и точки входа |
| Изменение файла/символа, Git diff, риск, тесты, доказательство связи | CodeSlicer | Bounded review, evidence, тесты |
| Вопрос «где находится и как устроено?» | Сначала Graphify, затем CodeSlicer при выборе символа | Карта → точная карточка |
| Сквозная цепочка UI/API/сервис/тест | Graphify для границ, CodeSlicer для подтверждённых связей | Два явно подписанных слоя |

## Базовый цикл

1. Для незнакомой папки вызовите `scan_plan`, затем `project_status`.
2. Если канонического графа нет — вызовите `analyze_project` с явными scope и budget при большом проекте.
3. Для ежедневной работы начинайте с `review`, а не с полного closure. Запрашивайте максимум 10 главных сущностей.
4. Для выбранного результата вызовите `inspect`; переходите к `investigate` только когда нужен ограниченный глубокий путь.
5. Покажите coverage, unresolved regions и confidence рядом с выводом. Не выдавайте Graphify overlay за canonical evidence.

## Работа с выбором и лимитами

- При `needs_selection` покажите кандидаты и попросите пользователя выбрать конкретный ID/файл; не выбирайте по догадке.
- У `investigate` всегда задавайте разумные `depth`, `max_nodes`, `max_edges`; сообщайте, если результат truncated.
- При ограниченном покрытии предложите нужный adapter, но не меняйте риск автоматически и не скрывайте ограничение.

## Approval и local-first

Обычное чтение, scan и статический анализ локальны. Для clone, запуска внешнего инструмента, тестов или network-варианта **сразу вызовите нужный MCP-инструмент с точными параметрами**. Без credentials он сам вернёт `status: pending_approval` и готовый approval record. Не собирайте `payload` вручную и не вызывайте `request_action_approval`, кроме редкого advanced сценария. Человек подтверждает запрос локально, затем агент повторяет тот же вызов с `approval_id` и `approval_token`.
